# Implementation details

The public GitHub repository contains canonical `skills/<name>/SKILL.md` folders.
Focused definition guides adapt `scripts/project.py` commands to their packaged
`scripts/definition.py`; Define a Project retains its canonical command.
The README links directly to the self-contained bootstrap skill. There is no
MCP/API publisher or separate website application. Existing GitHub Pages hosting
serves the public static examples from `main`; it is configured outside the
repo-owned Makefile workflow. Private skills and personal context
belong in a separate private repository.

## Catalog and packages

`scripts/skills.py` uses Python 3.10+ and only the standard library. `list` reads
names and descriptions directly from canonical skills; no separate editable
catalog duplicates them. `check` validates the restricted frontmatter described
in CONTRIBUTING, names, package layout, manifests, assembled payloads and credential
signatures. It rejects links (including Windows junctions/reparse points), hidden
files and caches. It does not execute skills or certify their instructions.

The CLI delegates to `scripts/skill_tools/`: `common.py` owns identity and
snapshots, `packages.py` owns payload composition and ZIPs, `installation.py`
owns safe updates, and `limits.py` owns the 300-line rule. Existing CLI commands
and the `scripts/skills.py` import facade remain available.

`scripts/check_code_size.py` checks tracked and nonignored new coding files,
including tests and maintained HTML/CSS/JavaScript. Comments, blank lines and a
final partial line count toward the 300 physical lines. Make check/build and CI
run it. Only the eight generated HTML deliverables under `examples/dynamic-umls/`
are exempt; their maintained inputs are checked. Package composition separately
rejects every delivered coding file over the limit before output creation.

`build` creates one ZIP per skill and a SHA-256 catalog in `dist/`. It packages
skill-local files plus explicitly selected shared scripts, with stable ordering,
timestamps, and executable flags. These outputs are ignored by Git. CI keeps
builds as artifacts; publishing a GitHub Release is a separate operation.
ZIP entries explicitly use Unix creator metadata (`create_system = 3`) to match
their POSIX permission bits, so the build host OS does not alter archive hashes.
The generated catalog uses UTF-8 and explicit LF newlines on every platform.
`.gitattributes` keeps text files at LF on every platform and marks PNG/ZIP
assets as binary, preserving canonical generated bytes on Windows checkouts too.

## Package composition

Every source skill has `assets/package.json`, separate from its behavioral
`assets/contract.json`. The manifest has exactly these fields:

```json
{
  "schema_version": 2,
  "scripts": [
    {
      "source": "shared/lifecycle/definition.py",
      "destination": "scripts/definition.py"
    },
    {
      "source": "shared/lifecycle/definition_validation.py",
      "destination": "scripts/definition_validation.py"
    }
  ]
}
```

Each `scripts` entry has exactly `source` and `destination`. Sources are literal
repository-relative `shared/<family>/<script>.py` paths; destinations are literal
skill-relative `scripts/<script>.py` paths. An empty list is valid. Manifest v2,
property names and types are strict. Implicit v1 filename maps, duplicate JSON
keys and duplicate destinations are rejected; a source may be reused with distinct
destinations. Existing installed ownership receipts remain v1.
There are no commands, templating, globbing, downloads or post-install hooks.
Skill-local scripts such as the manager's `manage.py` stay local when unshared.
For example, setting `"destination": "scripts/project.py"` installs the same
definition source under a different entry-point filename. Include required
sibling modules explicitly; the assembler does not
infer dependencies from imports. Definition delegates validation to
`definition_validation.py`; workflow delegates to `workflow_input.py` and
`workflow_rules.py` while preserving its existing public functions and callbacks.

One byte/mode payload function feeds `check`, `assemble`, installation and ZIP
builds. Package metadata itself is excluded from delivered files. Scripts retain
their existing sibling filenames and import behavior; each delivered skill needs
neither the checkout nor another installed skill. `assemble --output <new-path>`
materializes selected standalone folders for local development; it refuses an
existing output and source-contained destinations. Runtime tests use disposable
assembled catalogs rather than sparse source folders.

Sources are restricted to literal shared family/script paths. The assembler rejects
missing files, reserved filenames, path escapes, absolute/drive/UNC paths,
symlinks/junctions in shared paths, local/shared destination collisions and
case-insensitive file/directory collisions. All payloads are validated and scanned
for known credential signatures before install or output creation. Findings expose
filenames only. As elsewhere, signature checks are heuristic, not a guarantee.

Ownership receipt format remains v1 and records hashes/modes/directories of the
assembled output. Byte-identical legacy installs remain no-ops; edited copies
still block all requested targets at preflight. A legacy complete-folder catalog
without `shared/` may omit package manifests, allowing already assembled folders
to remain independently usable. Raw source-folder copying from this repository
is no longer an installation method: use our installer, assembled folders or ZIPs.
Static guide/template copies remain governed by their existing generators; this
change removes script duplication rather than redesigning those generators.

## Safe installation

`install` targets the user-level paths listed in README. It explicitly installs
requested agents without guessing whether their apps are installed. `--skill`
selects individual catalog entries; without it the current catalog is selected.
`--home` supports isolated tests and `--dry-run` makes no filesystem changes.

The bootstrap skill offers individual selections and an explicit "Install all
skills" option. The latter selects the full catalog for the requested agent;
installing for all three agents is a separate target choice.

The installer preflights every requested skill and target before making changes.
Each target directory holds `.context-templates-install.json`, identifying this
repository and recording content hashes and executable flags for managed copies.
It refuses same-name files, directories, or links without a valid managed record.
For managed copies it rejects edited, added, removed, or executable-bit-changed
files and directory additions/removals. Unchanged copies are left untouched.

Updates assemble a complete payload, verify its hashes, recheck source inputs
and the destination, then replace it while retaining the previous copy until the
ownership receipt is written.
Failure writing that receipt restores the previous copy. Errors stop the run;
if an unexpected I/O failure happens after earlier targets completed, those
completed targets remain installed. A subsequent safe rerun resumes. Run only
one installer process per destination at a time.

No unrelated skill is scanned for removal. Skills removed from the source catalog
are not automatically pruned from machines. Keep the ownership receipt: losing
it makes an existing same-name skill an unmanaged conflict. Never change it to
silence a real local-edit conflict. Installed copies are snapshots, so local edits
do not modify the canonical repository and Git changes do not silently alter
installed instructions.

## Contribution and validation boundary

The bootstrap skill distinguishes local updates from upstream improvements.
Only an authorized contribution creates a branch, commit, push, and PR. It uses
GitHub CLI when available, forks for contributors without upstream write access,
checks for duplicate PRs, and leaves merge decisions to maintainers. It carries
no credentials and does not require another skill or connector.

`make check` runs canonical diagram drift checks, catalog validation, and isolated
installer/package/rendering tests.
`make build` exercises packaging. The read-only GitHub Actions workflow runs
these checks on Linux, macOS, and Windows. Local results, CI, file installation,
agent discovery, invocation, PR submission, and maintainer acceptance are distinct
proof stages. There is no staging environment for this repository.

## Project definition

The assembled `ct-product-define-project/` is a standalone portable skill. Its
`scripts/project.py` (sourced from `shared/lifecycle/definition.py`) uses only
Python 3.10+ standard-library modules to validate
intake JSON, maintain a project-scoped event ledger, check a definition against
the current input/history digests, and render a Markdown brief. No commands
execute project code, access a service, or install dependencies.

Question usage is derived from recorded `ask` events, including unanswered
questions: no more than ten questions in two batches. Decision dependencies must
be resolved before their question's batch. Pending batches prevent further
batches. Submitted answers retain source text and qualifications; recommendations
do not resolve questions. New facts and adaptive branches use distinct event
types. Same-event retries are no-ops. Starting again with the same input preserves
the ledger. A changed input, stale revision, duplicate ID, or existing lock stops
the update; validated updates use an atomic replacement. The ledger is a
cooperative consistency guard, not protection against deliberate history edits.

Output validation preserves input constraints and tracking declarations, binds
all settled decisions, and requires each unresolved decision to be carried as an
assumption or actionable blocker. Unanswered questions and blocking decisions
require blockers; these forbid `ready-for-planning`. GitHub repository/Project
references may be unknown at definition time, but executable task publication
must subsequently verify and use both. No remote state is claimed by this skill.
New readable outputs refuse overwrite. See the bundled
[contract](skills/ct-product-define-project/references/contract.md) for exact
formats, commands, and the boundary between structural checks and agent judgment.

Focused tests cover the limits, negative controls, adaptive and resumed sessions,
stale artifacts/writes, retry behavior, output preservation, and CLI execution
from isolated copies for all three installer targets and a built ZIP. These are
package-level checks, not proof of discovery in a live agent runtime.

## Lifecycle routing and domain checks

The manager's `assets/catalog.json` defines twenty-one lifecycle identities. The
guide routes from the current definition, task graph, repository, verified
tracking and specialist reports; explicit specialist requests can enter directly.
It does not run every skill or execute selected work by returning a route.
`local_only` prevents remote tracking reads and holds execution before GitHub
admission. A stored tracking receipt cannot substitute for live readback.

Plan Development validates complete requirement coverage, unique task/criterion
IDs and an acyclic task graph. It prepares deterministic issue bodies with stable
plan/task markers and source digests. Its verifier uses read-only GitHub CLI
REST/GraphQL operations to check issue identity/content, duplicates, Project
membership and Status. New tasks must be open and in Backlog; the guide's ongoing
mode allows progression but requires matching closed issues, configured completion
statuses and scoped task proof before treating a task as complete. Task proof
preserves every planned acceptance criterion and its verification instruction.
Completed task evidence may retain an ancestor revision as later work advances;
review, QA, security and release gates require the current candidate. The current
adapter supports GitHub.com Projects v2. Live verification requires GitHub CLI,
authentication and access; unavailable readback blocks admission. The tool never
creates or changes remote tasks itself.

Eighteen specialists carry a domain policy in `assets/contract.json`, intake and
output examples, and package manifests selecting the shared validator. This is a small
explicit policy vocabulary, not an implementation of general JSON Schema. Rules
check domain relationships such as architecture endpoints, selected acceptance
coverage, before/after command identity, viewport coverage, QA environment and
journey identity, release phase evidence, launch authorization/readback and
product/market source links. Checked file references and canonical input digests
reject missing, stale, wrong-project or dropped-constraint outputs.

Repository bindings include HEAD and a structured working-tree fingerprint;
recorded successful commands must match both. Untracked files are fingerprinted
with separate filename/content-digest records so different file boundaries cannot
alias. Passing checks, earlier failing reproductions and incomplete observations
remain distinct. `workflow.py record` runs only argv explicitly supplied by its
caller, without a shell, with a bounded timeout and output reserved before
execution. Existing output prevents execution; no command is retried. Store proof
outside the measured tree or in an ignored directory. These local cooperative
checks cannot authenticate a manual approval or make arbitrary captured data true.

Canonical shared Python support lives once in `shared/lifecycle/`: definition,
workflow, planning, interface, store-release and configuration helpers. Per-skill JSON
manifests select their delivered filenames. `scripts/ct_lifecycle.py` continues
to synchronize guides and synthetic example hashes; `make resources` refreshes
those non-script outputs, and check/build reject drift. All twenty-one skills can
be installed separately. The guide explicitly reports a required specialist
that is unavailable.

Local tests cover each domain's blocked and ready artifacts, negative cases,
resumption, source drift, constraint retention, actual command capture in
disposable Git workspaces, routing and standalone CLI execution for all three
installation targets. Independent dry runs exercise local planning, a real
temporary bug fix, failed QA and a blocked release. Provider APIs are mocked in
tests; actual agent discovery, provider integrations, deployed application behavior
and human acceptance are separate evidence levels.

## Interface correction across a project

`ct-design-fix-interface` handles a reported visual/interaction defect directly,
without requiring a new product definition. It separates clear expected behavior,
confirmed same-cause occurrences, preserved intentional variants and uncertainty.
Uncertainty maps to actual pending questions in the shared scope ledger and holds
the affected source file and declared shared owners unchanged. Completed
clarification must have a recorded answer. The agent traces semantic aliases, shared consumers and route/state
variants beyond literal search, and uses a scoped owner repair rather than a
blind global replacement.

Its description and Codex `agents/openai.yaml` display metadata include UI, UX,
frontend and FE terms. These identify the correction workflow; the canonical
skill name stays `ct-design-fix-interface`. Metadata validation does not establish
that a host's picker indexes every field; verify search behavior in that host.

The interface and manager manifests select `shared/lifecycle/interface.py` as
`scripts/interface.py` in their independent assembled packages. Its read-only scan
captures bounded Git-listed frontend files and literal match identities without
source-line contents. Checked baseline/final inventories require each match to be
classified exactly once. Baseline source must match the failing reproduction;
the final scan is regenerated from the current source. Fixed occurrences require
linked rendered surfaces, declared viewport coverage, PNG identity/dimensions,
visual inspection observations and passing interaction/regression/build evidence.
A completed report cannot retain uncertain occurrences. These cooperative checks
cannot prove semantic completeness, visual quality, browser authenticity or human
acceptance. Runtime captures, source scans and ledgers remain private.

Resource synchronization generates the interface example's input digest from
public synthetic JSON.

## Store release specialists and public-content checks

The Apple and Android release skills share an offline store contract helper.
The Apple, Android and manager package manifests select
`shared/lifecycle/store_release.py` and `shared/lifecycle/configuration.py`.
The guide can route each platform directly and
validates its store receipts with the same rules. Known-app releases do not need
a new product definition, but supplied interview/definition history is checked.

Before release, `discover` produces a checked configuration inventory and
location/action/owner/verification setup plan; `configure` covers scoped local
setup and web wrapping. Discovery reads project/dependency hints and environment
names/locations without parsing `.env` values or signing files. Recognizable
private files must be ignored and untracked before source hashing. Literal source
references are checked for inventory coverage; arbitrary loaders, effective native
settings and capabilities still require agent inspection. Native target/config,
web output, SSR backend plan, secret exposure and wrapper sync/smoke proof are
gated separately from provider milestones. See each skill's setup and contract
guides for framework-specific configuration locations.

Both store examples are synthetic blocked discovery intakes. `make resources`
generates their `input_sha256` from their included sorted-key compact UTF-8 JSON;
check/build reject stale values. The `hash-input` CLI computes the same digest
for private runtime intake. File references hash actual bytes and the package
builder generates ZIP checksums; these hashes are content identifiers.

Store contracts bind the provider app and bundle/package IDs, version/build,
source revision, exported artifact digest, target stage/track, audience, countries
and rollout. Separate structured provider readbacks distinguish processing,
testing access, review submission and public release. A provider-confirmed review
exemption is distinct from pending/rejected review. Device proof is a separate
candidate-bound artifact. Production requires matching testing evidence, structured
human acceptance and action-scoped authorization. These cooperative records do
not authenticate approvals, prove signing validity or contact a provider.

`make check` runs `scripts/secret_scan.py` over tracked and nonignored untracked
public files. `make build` and CI also scan current catalog ZIP contents, using
redacted credential signatures and credential-file checks. `--history` additionally
checks all reachable Git blobs. This is a heuristic guard, not a guarantee that
all secrets are detectable. It never validates tokens or prints matched values.
New public examples use synthetic names; runtime evidence remains private.

`make setup-hooks` installs the opt-in pre-commit configuration for contributors;
it does not run during skill installation. Its repository scanner uses `--staged`
to inspect changed index blobs rather than the working copy, including force-added
ignored files. Gitleaks independently checks staged changes with redacted output.
`make secret-check` runs both scanners over reachable Git history, with the
repository scanner also checking current public files. The separate `Scan secrets
and history` CI job checks a full checkout and installs Gitleaks 8.30.1 from its
official release with a pinned archive SHA-256. It uses the free CLI directly,
not the separately licensed GitHub Action wrapper. Updating the CLI version in CI
requires updating its checksum as well. GitHub repository secret scanning and push
protection are administrator-managed controls, independent of these local files.

## Dynamic UMLs

The `ct-dynamic-uml` router owns the HTML template, authoring guide, supplied
Ginylil PNG, six diagram-type examples and an additional long sequence model
(32 messages, six participants). Shared renderer/verifier scripts live in
`shared/dynamic-uml/`, selected by each diagram package manifest.
`scripts/dynamic_umls.py` assembles a disposable router for contributor-only
rendering, synchronizes static resources into focused folders and generates standalone
review pages plus a gallery. The files work offline and are also served by the
repository's existing GitHub Pages hosting; generation does not configure hosting.

`make examples` refreshes generated files; check mode fails on drift. Each focused
skill installs and renders independently with no dependency on the router being
installed. `scripts/render.py` checks model identifiers, notation, bounds, active
edge endpoints, source link schemes and required scope text. It safely embeds
JSON, renders model text through DOM textContent, and exclusively creates output
files to preserve user artifacts. Coordinates and line routes are authored rather
than automatically laid out. Flowchart validation enforces at most seven nodes
per view, downward forward routes, orthogonal explicit ports, outer side loops,
node spacing, no connector overlaps/crossings and no routes through nodes. The
standalone `scripts/validate_flowchart.py` accepts JSON or emitted HTML and checks
every child view. It uses conservative node bounds; typography-dependent label
collisions still require rendered inspection. Nested `subflows` are embedded full
models referenced by double-bar subprocess nodes, with local references and
maximum nesting depth four. State diagrams use the same geometry policy,
with horizontal or vertical orientations, outer returns, self-transitions and
state-only detail views. `scripts/validate_state.py` verifies state JSON or HTML;
`labelOn` selects an actual straight segment, with conservative text-fit and
collision checks. The SVG viewer measures actual text for its opaque backing.
Floating state `labelAt` coordinates are rejected. State detail views explain
structure without simulating hierarchical execution semantics.

The test suite exercises all six renderers from isolated destinations for all three
agents, preserves existing HTML files, rejects unsafe/invalid model content and
checks canonical copies. Optional browser proof uses an existing Playwright runtime
and verifies local offline interaction and responsive layouts. Neither lane proves
that a real agent discovered the skill or followed the investigation/question policy.

The viewer defaults to a full-width diagram with details disclosed through an info
modal. Opening it pauses the current timer and saves its remaining duration; close
or Escape restores prior playback intent. A manually paused walkthrough stays
paused. The optional sidebar uses the same details DOM, narrows the diagram and
keeps its contents current. All six diagram canvases expand to their content height;
the document owns vertical scrolling. Narrow views pan horizontally without an
inner vertical canvas scrollbar. Sequence headers sit outside the horizontal
overflow container and stick below the playback controls; their width and pan
position stay aligned with the lifelines. Auto-follow checks the active message's
geometry in the visible window, accounting for both sticky regions. Sequence
auto-follow includes visible previous/next arrows when the combined height fits;
otherwise it prioritizes the active exchange. Structural views prioritize the
destination when a transition spans more than one viewport.
State diagrams fit the available width when event labels stay at least 10px.
Sequence walkthroughs always retain the active step participants and message
endpoints. Add participants from the previous and next chronological messages
first, then nearby participants while readable boxes and omission markers fit.
Show the entire sequence when it fits; only overflow groups become selectable
ellipses, preserving source order. Recalculate on step changes, window resize and
sidebar toggles. At very narrow sidebar widths, outer omission markers yield space to participant
names; internal omission markers remain. Only arrows whose endpoints are shown
remain visible; message numbers and chronological vertical positions are
preserved. Headers and arrows adapt to the canvas width without horizontal
panning. Overview restores the canonical full
layout and every message, with a visible horizontal-pan hint when needed.

Scenario selection uses a themed button/listbox below the trigger, with keyboard
navigation, committed selection, typeahead and dismissal. Subprocess inspection
offers Explore subprocess; changing views pauses playback. Back restores parent
scenario, step, overview, scroll and originating node focus. The supplied logo
is embedded unchanged as a PNG data URL, including in the local gallery. The
transparent mark is 40px (32px on narrow diagram pages), with 80% opacity and no
backing tile. Every diagram footer repeats the same embedded logo as a 32px
mark beside the domain link. Back also restores the parent document scroll
position for nested views.
